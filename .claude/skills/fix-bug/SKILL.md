# Fix Bug

Исправляем по фактам, а не угадыванием причины. Минимальное исправление, подтверждённое regression-тестом.

## Процедура

1. **Воспроизведи проблему.** Найди точные шаги/вход, при которых баг проявляется. Если не удаётся воспроизвести — не правь код наугад, собери больше данных.

2. **Зафиксируй ожидаемое и фактическое поведение.** Чётко: что должно происходить vs что происходит.

3. **Найди root cause.** Прочитай реальный код по пути выполнения (handler → `utils/*` → `db.py`). Не останавливайся на симптоме — найди настоящую причину. Проверь логи (структурные события из `utils/logger.py`).

4. **Добавь regression-тест.** Тест, воспроизводящий баг (моки БД/Telegram, фикстуры из `tests/conftest.py`).

5. **Убедись, что тест падает ДО фикса.** Запусти `pytest <новый тест>` — он должен упасть. Это доказывает, что тест ловит именно этот баг.

6. **Внеси минимальное исправление.** Меняй только то, что нужно для устранения root cause. Никакого попутного рефакторинга. Соблюдай границы слоёв из [CLAUDE.md](../../../CLAUDE.md) (SQL в `utils/*`, и т.д.).

7. **Прогони связанные тесты.** `pytest` по затронутым модулям, затем полный прогон. Новый тест теперь проходит, остальные не сломаны.

8. **Проверь отсутствие побочных изменений.** `git diff` — только целевое исправление и тест, без случайных правок.

## Инфраструктурные баги — сначала собери факты

Если симптом похож на проблему окружения/рантайма (бот не отвечает, зависает, дублирует сообщения, отваливается polling), **до правки кода** собери факты:

- **Процессы и контейнеры:** запущен ли `money_bot`, его статус/healthcheck (`docker ps`, `docker inspect`, `docker logs money_bot --tail`). Сколько экземпляров.
- **Второй экземпляр бота:** не запущен ли бот дважды (локально + на сервере) с одним токеном — это классическая причина «команды не принимаются» при PTB polling (конфликт `getUpdates`).
- **Polling/webhook:** бот работает на `run_polling` (см. `main.py`). Проверь, не выставлен ли случайно webhook, нет ли конфликта.
- **Proxy:** сервер в РФ ходит в Telegram через SOCKS5/`HTTPS_PROXY` — проверь доступность прокси и переменную окружения.
- **Состояние Telegram API:** доступность api.telegram.org, ошибки `getUpdates`/`Conflict`/`Flood`.
- **Логи:** структурные события и ошибки (`log_error`), scheduler/фоновые задачи (APScheduler) — не блокируют ли они event loop.

Только после сбора фактов формулируй root cause и переходи к шагам 4–8.
