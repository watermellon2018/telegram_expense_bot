# Verify Task

Независимая проверка выполненной работы. **Не правь код сразу** — сначала только верифицируй и выдай вердикт. Относись к коду скептически, как внешний ревьюер: не считай работу правильной по умолчанию.

## Процедура (только проверка)

1. **Соответствие задаче.** Перечитай исходную задачу. Делает ли реализация именно то, что просили — ничего меньше, ничего лишнего «заодно».

2. **Покрытие сценариев.** Все ли ветки реализованы: happy path, пустые данные, несуществующие сущности, отказ в правах. Что осталось незакрытым.

3. **Незапланированные изменения.** `git diff` целиком. Нет ли правок за пределами задачи, случайных переформатирований, отладочного кода, закомментированных блоков, изменённых несвязанных файлов.

4. **Тесты.** Запусти `pytest`. Есть ли тесты на новую логику. Действительно ли они проверяют поведение, а не просто «зелёные». Проходят ли все.

5. **Миграция.** Если есть SQL-миграция в `migration/` — идемпотентна ли (`IF NOT EXISTS`), совместима ли с существующими данными (nullable/default для новых колонок), лежит ли в `migration/<feature>/`. Применяется вручную (не автоматически на старте).

6. **Конкурентность.** Атомарны ли составные операции записи (`async with db.transaction()`). Нет ли гонок (read-modify-write без транзакции), особенно в проектах с несколькими участниками и в фоновых задачах APScheduler.

7. **Права доступа.** Проектные операции проходят через `utils/permissions.py` (`has_permission`/`require_permission`)? Нет ли пути, где чужой пользователь видит/меняет данные проекта без проверки роли. Личные данные (`project_id=None`) не утекают между пользователями.

8. **Безопасность выката.** Параметризованный ли SQL. Не логируются ли секреты. Нет ли изменения схемы, несовместимого со старой версией кода (если миграция и код катятся не атомарно). Нужны ли env-переменные/ручные шаги, которых ещё нет.

## Вывод

Выдай структурированный вердикт: **GO / NO-GO**, список найденных проблем по серьёзности, что осталось непокрытым, какие ручные действия нужны. Предложи исправления, но **не вноси их**, пока пользователь не попросит (тогда — через `/fix-bug` или напрямую).
