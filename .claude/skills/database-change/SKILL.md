# Database Change

Изменение схемы PostgreSQL. В проекте **нет Alembic** — миграции это сырые `.sql` файлы в `migration/<feature_NN_имя>/`, применяемые вручную через `psql`/asyncpg. *(На будущее: планируется переход на Alembic — пиши миграцию так, чтобы её было легко портировать в `upgrade()`/`downgrade()`.)*

## Процедура

1. **Изучи текущую схему.** Прочитай существующие миграции в `migration/` и SQL-запросы в `utils/*`, чтобы понять реальные таблицы/колонки/типы/ограничения (canonical-схемы в одном файле нет — она собирается из миграций и кода).

2. **Совместимость с существующими данными.** Таблицы непустые (прод работает). Новая NOT NULL колонка без default сломает существующие строки — добавляй либо `nullable`, либо с `DEFAULT`/backfill. Сужение типа/ограничения — проверь, что текущие данные ему удовлетворяют.

3. **Напиши миграцию (идемпотентно).** Файл в `migration/<feature>/`. DDL оборачивай:
   ```sql
   DO $$ BEGIN
     IF NOT EXISTS (SELECT 1 FROM information_schema.columns
                    WHERE table_name='...' AND column_name='...') THEN
       ALTER TABLE ... ADD COLUMN ...;
     END IF;
   END $$;
   ```
   Аналогично для таблиц/ограничений/индексов (`CREATE TABLE IF NOT EXISTS`, проверка `pg_constraint`).

4. **Проверь «upgrade».** Прогони SQL на локальной/тестовой БД. Затем прогони **повторно** — идемпотентность означает, что второй запуск не падает.

5. **Продумай «downgrade».** Опиши обратный SQL (DROP COLUMN/TABLE/CONSTRAINT) — хотя бы в комментарии или отдельном файле, чтобы откат был возможен. Оцени потерю данных при откате.

6. **Server defaults.** Для новых колонок реши: `DEFAULT` на уровне БД (применится к существующим строкам сразу) или значение в коде. Зафиксируй выбор явно.

7. **Nullable-переходы.** Переход `NULL → NOT NULL` делай в два шага: добавить nullable + backfill данных, затем `SET NOT NULL`. Не вешай NOT NULL на колонку, где уже есть NULL.

8. **Индексы и ограничения.** Нужны ли индексы под новые запросы (по `user_id`, `project_id`, датам). Уникальные ограничения — проверь, что текущие данные не нарушают их (иначе `ADD CONSTRAINT` упадёт).

9. **Не редактируй применённые миграции.** Уже выкаченные `.sql` — иммутабельны. Любое изменение — новый файл миграции, не правка старого.

10. **Блокировки больших таблиц.** `ALTER TABLE`, добавление индекса/ограничения берут блокировку. На большой таблице `expenses` это может надолго заблокировать бота. Для индексов рассмотри `CREATE INDEX CONCURRENTLY`; оцени время и влияние на прод.

## Вывод
Готовый `.sql` файл + краткая записка: что меняется, обратный SQL, нужен ли backfill, риски блокировки, ручные шаги применения. Применение к реальной БД — **только с явного разрешения** (см. [CLAUDE.md](../../../CLAUDE.md)).
