# Deploy Check

Проверка готовности к деплою. **Не деплой самостоятельно** — деплой (`deploy.yml`, `docker compose up`, push в GHCR) требует отдельного явного разрешения (см. [CLAUDE.md](../../../CLAUDE.md)). Этот skill только диагностирует и выдаёт GO/NO-GO.

## Контекст деплоя
Деплой: push в `master` → GitHub Actions `deploy.yml` на **self-hosted** раннере → build + push образа в **GHCR** (`ghcr.io/.../money_bot:<tag>`) → `docker compose pull/up -d` → healthcheck → авто-rollback при провале (`rollback.yml`). Контейнер `money_bot`, метрики `:8010→:8000`.

> **Docker-демон не запускать.** На машине пользователя Docker Desktop не работает. Не пытайся стартовать Docker Desktop/демон и не жди его поднятия. Проверки делай статически (чтение файлов). Команды, требующие демона (`docker build`, `docker compose up/pull/run`, `docker ps`), не выполняй — если такая проверка нужна, пометь её как «проверить на сервере/в CI». `docker compose config` (валидация YAML) демон не требует — допустимо.

## Проверки

1. **Docker build (статически).** `Dockerfile` корректен (база `python:3.11-slim`, `COPY`/`CMD` на месте) и `requirements.txt` консистентен (всё, что импортирует код, есть в зависимостях). Живой `docker build` не запускай (нужен демон) — оцени по содержимому файлов; реальную сборку выполняет CI/сервер.

2. **Конфигурация compose.** `docker-compose.yml`: имя контейнера, `env_file`, volume `telegram_bot_data/users:/app/data/users`, внешняя сеть `postgres_net`, проброс порта метрик, label для promtail. Ничего не сломано относительно того, что ожидает сервер.

3. **Наличие миграций.** Если изменения требуют новой схемы БД — есть ли соответствующий `.sql` в `migration/<feature>/`. Если код ожидает новую колонку/таблицу, а миграции нет — **NO-GO**.

4. **Порядок: миграция → бот.** Миграции применяются **вручную и до** выката кода (авто-применения на старте нет). Проверь, что новый код не упадёт, если миграция ещё не применена, и наоборот — старый код переживёт уже применённую миграцию (forward/backward совместимость на время выката).

5. **Переменные окружения.** Новые env-переменные, которые читает код (`config.py`, `utils/db.py`), должны быть добавлены в секцию `.env` деплой-воркфлоу (`deploy.yml`) и в GitHub Secrets. Перечисли все требуемые: `TELEGRAM_BOT_TOKEN`, `DB_*`, `HTTPS_PROXY` и любые новые.

6. **Healthcheck.** Healthcheck в compose присутствует и осмыслен; контейнер успеет подняться в `start_period`.

7. **Логи.** Структурное JSON-логирование работает (promtail-label); нет шумного спама и нет логирования секретов.

8. **Rollback.** Механизм отката рабочий: `previous_version` сохраняется, `rollback.yml` доступен. Откат кода не конфликтует с уже применённой необратимой миграцией (если миграция необратима — отметь это явно как риск).

9. **Несовместимые изменения схемы.** Нет ли DROP/переименований колонок, которые сломают работающий прод между миграцией и выкатом. Помечай как высокий риск.

10. **Секреты в diff.** `git diff` не содержит токенов, паролей, DSN, содержимого `.env`. `.env` не закоммичен.

11. **Версии образов.** Тег образа уникален (timestamp+sha), `latest` обновляется. Нет рассинхрона версий в compose.

12. **GHCR workflow.** `deploy.yml` имеет `packages: write`, корректный логин в GHCR, build-push настроен.

## Вывод
**GO / NO-GO** + список блокеров и рисков по серьёзности + чек-лист ручных шагов (применить миграцию, добавить секреты, и т.д.). Сам деплой — только после отдельного разрешения пользователя.
