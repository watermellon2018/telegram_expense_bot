# Implement Feature

Полноценная реализация новой функции. Не пиши код сразу — сначала исследуй, потом реализуй, потом проверь. Следуй [CLAUDE.md](../../../CLAUDE.md): SQL только в `utils/*`, команды в `handlers/registry.py`, тексты кнопок в `config.py`, структурное логирование.

## Процедура

1. **Исследуй существующую реализацию.** Найди, где живёт смежная логика. Прочитай соответствующие модули в `handlers/*` и `utils/*`. Определи, это новая команда, новый доменный use-case или расширение существующего.

2. **Найди аналогичный паттерн и копируй его.** В проекте однородные паттерны — найди ближайшую по смыслу фичу (расход/доход/проект/бюджет/кэшбэк) и повтори её структуру: как handler вызывает `utils/*`, как формируется клавиатура, как идёт диалог `ConversationHandler`, как логируется. Не изобретай новый стиль.

3. **Проверь права доступа.** Если фича касается проектных данных — определи нужный `Permission` в `utils/permissions.py`. Операции с проектом обязаны проходить `has_permission`/`require_permission`. Личные операции (`project_id=None`) разрешены владельцу. Уточни, нужно ли новое значение в `Permission` enum и `ROLE_PERMISSIONS`.

4. **Определи изменения данных и БД.** Какие таблицы/колонки нужны. Сверься с существующей схемой (читай `migration/` и SQL-запросы в `utils/*`). Реши, нужна ли миграция вообще.

5. **Создай миграцию (если нужна).** В проекте **нет Alembic** — миграции это raw `.sql` в `migration/<feature_NN_имя>/`. Пиши **идемпотентно**: `DO $$ BEGIN IF NOT EXISTS (...) THEN ... END IF; END $$;` для DDL. Учитывай совместимость с существующими данными (nullable / server default для новых колонок на непустой таблице). При сложных изменениях вызови `/database-change`. *(На будущее: проект планирует переход на Alembic — структурируй миграцию так, чтобы её легко было портировать.)*

6. **Реализуй код.** Доменная логика и SQL — в `utils/*` (параметризованные запросы `$1, $2`, атомарность через `async with db.transaction()`). Handler — только оркестрация и формат ответа. Новую команду зарегистрируй в `handlers/registry.py` с правильным порядком (помни: `expense.text_handler` ловит любой текст и идёт последним). Тексты кнопок — в `config.py`. Логируй через `utils/logger.py`.

7. **Добавь тесты.** Покрой happy path, права доступа и краевые случаи. Моки БД/Telegram, фикстуры из `tests/conftest.py`. Подробный чек-лист сценариев — `/add-tests`.

8. **Запусти проверки.** `pytest` (локально может потребоваться conda-окружение `telegram_bot`). Все тесты должны проходить.

9. **Проверь diff.** `git diff` — убедись, что нет лишних/случайных изменений, отладочного кода, закомментированных блоков, утечки секретов.

10. **Перечисли ручные действия.** Явно выпиши, что человек должен сделать руками: применить SQL-миграцию (`psql`/asyncpg, не автоматически), добавить переменные окружения в `.env` и GitHub Secrets, обновить документацию (`/update-docs`), любые шаги деплоя.
